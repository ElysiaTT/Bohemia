一套好的工作流，未必需要很多工具。它首先应当让你知道：事情从哪里开始，文件放在哪里，下一步应该做什么。

如果每次开始工作，都要重新寻找入口，那么值得优化的也许不是速度，而是那些反复发生的小阻力。

## 先找到重复出现的阻力

不要急着重做整个系统。可以先观察几天，记下最常出现的停顿：找不到文件、命令忘记怎么写、同一段说明重复整理。

挑出其中一项，做一个最小的改进。比如统一文件夹名称，把常用命令放进项目脚本，或者给经常重复的操作写一页说明。

## 让结构服务于寻找

目录不必深，也不必复杂。能让未来的自己找得到，就已经完成了最重要的任务。

```text
my-project/
├── README.md       # 从哪里开始
├── notes/          # 思考与记录
├── src/            # 正在构建的内容
└── archive/        # 已结束的阶段
```

一种容易理解的命名方式，往往比增加一层分类更有帮助。

## 把重复步骤收进脚本

当一组命令反复出现，可以把它们变成一个有意义的入口。

```json
{
  "scripts": {
    "dev": "astro dev",
    "check": "astro check",
    "build": "astro build"
  }
}
```

脚本不是为了显得专业，而是为了减少记忆负担。名称清晰，错误容易看见，才方便长期使用。

## 允许系统保持简单

一种新工具需要学习，一套新规则需要维护。在加入它们之前，可以先想一想：它解决了哪个已经出现的问题？

如果暂时没有明确答案，也许可以继续使用现有的方法。

工作流的价值，最后仍然体现在工作本身。它让开始更轻松，让结束更清楚，也让注意力更少被琐事打断。
